Codexの回答は、そのままでも十分読めます。

ただ、日本語だけもう少し自然にしたい場面があります。そこで最後にGeminiへ「自然な日本語にして」と渡してみたところ、文章は読みやすくなる一方で、意味まで少し変わることがありました。

たとえば元の文が、

> Bより安いからではなく、保守の手間が小さいためです。

だったとします。

Geminiに普通に書き直させると、実際の評価ではこうなりました。

> Bよりも安価だからという理由だけでなく、保守の手間が小さいためです。

前者は「安さは理由ではない」。後者は「安さも理由の一つ」です。

日本語を整えたいだけなのに、判断まで変わっています。

そこで、**Codexで内容を確定し、Geminiには日本語の表面だけを触らせる**仕組みを作りました。

## 役割を分ける

構成は単純です。

```text
Codexで調査・判断・実行まで終える
  ↓
数字やURLなどを機械的に保護
  ↓
Geminiで日本語だけ整える
  ↓
保護した値を元に戻す
  ↓
Markdown構造を機械検証
  ↓
Codexで意味を最終確認
```

Geminiには検索履歴やツール実行履歴を渡しません。渡すのは、Codex側ですでに内容を確定した最終原稿だけです。

Geminiを2人目の判断役にしないのが一番大事な点です。

## 壊されたくない値は、そもそも触らせない

「数字を変えないで」と指示するだけでは不安が残ります。

そこでGeminiへ送る前に、日付やURL、コード、金額などを一時的な記号へ置き換えます。

```text
2026年9月4日
↓
⟦LOCK_0001⟧

`npm run build`
↓
⟦LOCK_0002⟧
```

主に保護しているのは次のようなものです。

- コード
- URLとリンク先
- 日付
- 金額、割合、単位付き数値
- ファイルパス
- バージョン文字列

Geminiの出力後、すべての記号が1回ずつ残っていることを確認して元に戻します。消えたり増えたりしていれば、その出力は使いません。

## 普通の書き直しでは何が起きたか

同じ原稿を、

1. Codexの原文
2. Geminiによる通常の書き直し
3. 今回の制約付き書き直し

の3通りで比較しました。モデルは `gemini-3.5-flash-lite` です。

通常の書き直しでは、次のような変化が実際に出ました。

- `## 実行方法` という見出しが消える
- `¥3,500` が `3,500円` に変わる
- 「意味まで動きやすくなる」が「意味まで変わってしまう」になり、断定が強くなる
- 「Aを推奨するとまでは言えない」が、Aを弱く推奨しているような表現に変わる

どれも文章としては自然です。ただ、元の意味や構造をそのまま保ちたい用途では困ります。

## 機械検証だけでも足りなかった

評価を19ケースまで増やすと、制約付きの書き直しでも問題が見つかりました。

元の文章では、

1. 移行が必要
2. A案を採用
3. A案は作業量が少ない

という3つの事実を並べていただけでした。

ところが、書き直し後は、

> A案は作業量が少ないためです。

となりました。

「作業量が少ないからA案を選んだ」という因果関係を、勝手に作ってしまっています。

Markdownの構造検証は通っていました。つまり、**形が壊れていなくても意味は動く**ということです。

そこで検証を2つに分けました。

コード側では、記号の欠落やMarkdown構造など、確実に判定できるものだけを見る。

意味については、Codexが原文と比較して、次を確認します。

- 事実
- 結論や推奨
- 肯定・否定
- 確信度
- 条件と例外
- 因果関係
- 「検討」「予定」「決定」「実施」といった段階

## 19ケースで調整した結果

日本語を積極的に直すようにした版では、今度は別の問題が出ました。

> この対応を実施するという方向性で進めることが適切であると考えています。

が、

> この対応を進める方向で検討するのが適切です。

に変わりました。

「実施する方向」が「検討」に戻り、「考えています」が断定に変わっています。

そこで最終版では、確信度を表す言葉と、検討・予定・決定・実施といった段階を勝手に変えないよう明示しました。

同じ19ケースで再評価した結果です。

| 項目 | 結果 |
| --- | ---: |
| 機械検証 | 19/19 PASS |
| 実行エラー | 0 |
| 原文から変更された出力 | 9/19 |
| 手動確認で見つかった重大な意味変化 | 0 |
| 平均API応答時間 | 728 ms |

もちろん19件を1回ずつ試しただけなので、これで安全性を証明できたわけではありません。

一方で、安全ルールを増やした分、19ケースの入力トークンは `7,340 → 12,755 → 17,980` と増えました。安全性とコストには分かりやすいトレードオフがあります。

## まとめ

作ってみて分かったのは、良い指示文を書くことよりも、**何をAIに任せ、何をコードで固定するかを決める方が重要**だということです。

数字やURLはお願いして守らせるより、触れないようにする。

Markdown構造はAIに聞くより、コードで確認する。

意味は別の工程で確認する。

そしてGeminiには調査も判断もさせず、日本語だけ整えさせる。

今のところ、この分け方が一番扱いやすいです。

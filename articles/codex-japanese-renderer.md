Codexを使っていると、内容はこれでいいけど文章だけ少し硬い、ということがあります。

だったら最後にGeminiへ渡して、日本語だけ直してもらえばいい。最初はそれで済むと思っていました。

実際にやってみると、普通に意味が動きました。

> Bより安いからではなく、保守の手間が小さいためです。

これを「自然な日本語にして」と渡した結果がこちらです。

> Bよりも安価だからという理由だけでなく、保守の手間が小さいためです。

読みやすくはなっています。でも意味は違います。

元の文では「安さは理由ではない」。書き直した文では「安さも理由の一つ」になっています。

文章だけ直してほしいのに、Geminiが中身まで考え直してしまった。

なので、Geminiに任せる範囲をかなり狭くしました。

## Geminiには文章だけ触ってもらう

流れはこんな感じです。

```text
Codexで調査・判断・実行まで終える
  ↓
数字やURLなどを一時的に隠す
  ↓
Geminiで日本語だけ整える
  ↓
隠した値を元に戻す
  ↓
Markdownの形を機械的に確認
  ↓
Codexで意味が変わっていないか確認
```

Geminiには検索履歴やツールの実行履歴を渡しません。Codex側で内容を確定したあと、その文章だけを渡します。

日付、URL、コード、金額、ファイルパスなどは、そもそも書き換えさせません。

たとえば、

```text
2026年9月4日
↓
⟦LOCK_0001⟧

`npm run build`
↓
⟦LOCK_0002⟧
```

のように一時的な記号へ置き換えてからGeminiへ送ります。戻すときに記号が消えていたり増えていたりすれば、その出力は捨てます。

## それでも意味は動いた

ここまでやれば十分かと思ったのですが、そうでもありませんでした。

評価を19ケースまで増やしたとき、元の文では、

1. 移行が必要
2. A案を採用
3. A案は作業量が少ない

と3つの事実を並べていただけなのに、書き直し後は、

> A案は作業量が少ないためです。

となりました。

勝手に理由を作っています。

Markdownの形も数字も壊れていないので、コードだけでは見つけられません。ここから、最後にCodexで原文と意味を見比べるようにしました。

もう一つ厄介だったのが、

> この対応を実施するという方向性で進めることが適切であると考えています。

が、

> この対応を進める方向で検討するのが適切です。

に変わったケースです。

文章はすっきりしています。ただ、「実施する方向」が「検討」に戻り、「考えています」も断定に変わっています。

この手の違いは、日本語として自然かどうかだけ見ていると簡単に見落とします。

今の版では、因果関係、確信度、「検討」「予定」「決定」「実施」のような段階を勝手に変えないよう明示しています。

同じ19ケースで試した結果はこうでした。

| 項目 | 結果 |
| --- | ---: |
| 機械的な確認 | 19/19 成功 |
| 実行エラー | 0 |
| 実際に文章が変わったケース | 9/19 |
| 手動確認で見つかった重大な意味変化 | 0 |

もちろん、19件を1回ずつ試しただけなので「安全になった」と言い切れるものではありません。

安全側に寄せるほど指示文も長くなります。19ケースの入力トークンは `7,340 → 12,755 → 17,980` と増えました。このあたりは普通にトレードオフです。

## この記事にも使ってみた

この記事の本文も、公開前にこの仕組みに通しています。

一発では通りませんでした。

最初の実行で、本文中の

> Aを弱く推奨しているような表現

が、

> Aを強く推奨しているような表現

に変わりました。

最後の意味確認で気づいたので、その出力は捨てました。そのあと「弱く / 強く」「少し / かなり」のような程度まで勝手に変えないルールを追加して、もう一度実行しています。

修正版では問題が出なかったので、この記事にはその結果を使っています。

仕組みの記事を書いて、その記事に仕組みを通したら、仕組みの穴が一つ見つかりました。

たぶん、これくらいの距離感がちょうどいいんだと思います。Codexに考えてもらって、Geminiには日本語だけ触ってもらう。意味が怪しければ、元の文に戻す。

今はその運用で使っています。

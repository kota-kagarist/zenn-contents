LLMの出力を、最後に別のLLMで「自然な日本語に直す」。

一見すると簡単です。実際、文章はかなり読みやすくなります。ただ、試してみると別の問題が出ました。

**自然にするつもりで、意味まで少し動く。**

たとえば元の文章が、

> Bより安いからではなく、保守の手間が小さいためです。

だったとします。

これをGeminiに普通に「自然な日本語にして」と渡したところ、実際の評価では次のような文になりました。

> Bよりも安価だからという理由だけでなく、保守の手間が小さいためです。

かなり自然です。でも意味は同じではありません。元の文では「安さは理由ではない」と言っているのに、書き換え後は「安さも理由の一つ」と読めます。

文章の表面だけを整えたいのに、推論までやり直されている。

そこで、CodexとGeminiの役割を明確に分ける小さな仕組みを作りました。

## Codexは考える。Geminiは日本語だけ整える

設計の原則はこれです。

> **Codex does the thinking. Gemini renders the Japanese.**

役割分担はかなり極端にしています。

```text
User request
  ↓
Codex
  ├─ 意図理解
  ├─ 調査
  ├─ 推論
  ├─ ツール実行
  ├─ 検証
  └─ 最終回答の意味を確定
  ↓
Protector
  └─ 壊されたくない値をプレースホルダー化
  ↓
Gemini
  └─ 日本語の表面だけ編集
  ↓
Restorer
  └─ 保護した値を完全一致で復元
  ↓
Deterministic Verifier
  └─ Markdown構造などを機械検証
  ↓
Codex Semantic Review
  └─ 意味・結論・確信度が変わっていないか確認
  ↓
Final output
```

Geminiには、Codexの思考過程や検索履歴、ツール実行履歴を渡しません。

渡すのは、**Codex側ですでに意味を確定した最終原稿だけ**です。

Geminiを「2人目のエージェント」にしないことが、この設計の一番大きなポイントです。

## プロンプトだけでは守り切れない

最初は、Geminiに強めの指示を書けば十分だと思っていました。

たとえば、

- 事実を変えない
- 結論を変えない
- 推測を断定にしない
- 数字を変えない
- 新しい提案を足さない

といったルールです。

ただ、実際に評価すると、それだけでは不安が残りました。

数字やURL、コマンド、バージョン番号のようなものは「変えないで」とお願いするより、**そもそも編集させない**方が確実です。

そこでGeminiへ送る前に、壊されたくない値を機械的に保護します。

```text
2026年9月4日
↓
⟦LOCK_0001⟧

`npm run build`
↓
⟦LOCK_0002⟧

https://example.com/docs
↓
⟦LOCK_0003⟧
```

現在は主に次のものを保護しています。

- fenced / inline code
- URLとMarkdownリンク先
- 日付
- 金額、割合、単位付き数値
- ファイルパス
- バージョン文字列
- `google-genai>=2.22,<3` のような依存関係指定

Geminiの出力後、すべてのプレースホルダーが**ちょうど1回ずつ**残っていることを確認して元に戻します。

1つでも消えていたり、逆に増えていたりしたら、その出力は採用しません。

自然さより正しさを優先して、fail closedにしています。

## 「普通に書き直す」と何が起きたか

評価では、同じCodex原稿を3パターンで比較しました。

- A: Codexの原文
- B: Geminiに普通に「自然な日本語にして」と依頼
- C: 今回の制約付きRenderer

Geminiには `gemini-3.5-flash-lite` を使っています。

最初の評価だけでも、Bの普通の書き直しではいくつか面白い壊れ方が出ました。

### 理由が変わる

先ほどの例です。

```text
Bより安いからではなく
```

が、

```text
Bよりも安価だからという理由だけでなく
```

になりました。

読みやすさは上がっていますが、因果関係が変わっています。

### Markdownの見出しが消える

技術文書では、`## 実行方法` という見出しが普通の書き直しで削除されました。

文章としては成立していても、Markdown文書としては構造が変わっています。

### リテラル表現が変わる

`¥3,500` が `3,500円` に変わったケースもありました。

人間には同じ意味に見えます。ただ、仕様書やログ、比較結果のように「その表記自体」を維持したい場面では困ります。

### 断定が強くなる

```text
意味まで動きやすくなる
```

が、

```text
元の意味まで変わってしまう
```

になったケースもありました。

微妙な差ですが、後者の方が明らかに強い表現です。

こういう変化は、単純な文字列比較では見つけにくいところです。

## 検証は二層に分けた

ここで悩んだのが「意味が変わっていないことをどう検証するか」でした。

最終的には、全部を1つのVerifierに背負わせるのをやめました。

### 1. コードで確実に判定できるもの

Python側では、決定論的に確認できるものだけを見ます。

- プレースホルダーの欠落・重複
- Markdown見出しの構造
- コードフェンス
- リンク先
- 箇条書き構造

ここは曖昧さがありません。

### 2. 意味を読む必要があるもの

一方で、次のようなものはCodex側で原文と比較します。

- 事実
- 結論、推奨
- 肯定・否定
- 確信度
- 条件、例外
- 因果関係
- 「検討」「予定」「決定」「実施」といった判断・作業段階

この分離は、後の評価でかなり重要だと分かりました。

## 19ケースに増やしたら、制約付きでも意味が動いた

最初の5ケースではかなり安全に見えたので、評価を19ケースまで増やしました。

わざと次のような厄介な日本語を入れています。

- AIっぽい冗長表現
- 名詞化の連続
- 接続詞の使いすぎ
- 長すぎる一文
- 判断保留
- 否定のスコープ
- 条件と例外
- 二重否定
- 引用
- Markdownとコマンド

この評価で、制約付きRendererにも弱点が見つかりました。

元の文章では、

1. 移行を進める必要がある
2. A案を採用する
3. A案は作業量が少ない

という3つの事実を並べていただけでした。

ところがRendererが、

> A案は作業量が少ないためです。

と書き換えました。

もっともらしいですが、**元の文章には「作業量が少ないからA案を選んだ」とは書いていません**。

決定論的なMarkdown検証は19/19でPASSしていました。それでも意味は動く。

ここで「構造検証だけでは十分ではない」とはっきりしました。

## 自然さを上げたv2では、別の意味が壊れた

次に、Rendererが保守的すぎる問題を直しました。

たとえば、

```text
実行を行う際には、`python -m pytest` を実行するという形で実施してください。
```

のような明らかに冗長な文まで、そのまま返すことがあったためです。

そこでv2では、

- 「実行を行う」→「実行する」
- 「まず最初に」→「まず」
- 不要な「〜となっています」を減らす
- 長い文は意味を変えない範囲で分ける

といった編集を明示的に許可しました。

自然さはかなり改善しました。ただ、今度は別の問題が出ました。

原文の、

> この対応を実施するという方向性で進めることが適切であると考えています。

が、

> この対応を進める方向で検討するのが適切です。

になりました。

これには2つの問題があります。

1つ目は、`実施する方向で進める` が `検討する` に戻っていて、判断・作業の段階が変わっていること。

2つ目は、`適切であると考えています` が `適切です` になり、話者の確信度が強くなっていることです。

見た目はすっきりしています。でも、これは表現整理ではありません。

## v2.1では「判断段階」と「確信度」を保護した

そこでv2.1では、安全ルールに次を追加しました。

- `〜と考えています`
- `〜の可能性があります`
- `〜とは言えません`

のような認識・確信度を示す表現は、冗長に見えても意味要素として扱う。

さらに、

- 検討
- 方針
- 予定
- 決定
- 実施
- 完了

といった段階も勝手に進めたり戻したりしないようにしました。

同じ19ケースで再評価した結果がこちらです。

| 項目 | v2.1 |
| --- | ---: |
| 決定論的検証 | 19/19 PASS |
| 実行エラー | 0 |
| 原文から変更された出力 | 9/19 |
| 手動レビューで見つかった重大な意味変化 | 0 |
| 平均APIレイテンシ | 728 ms |

単発の評価なので、これを統計的な性能値として扱うつもりはありません。

LLMの出力は確率的です。19件で問題がなかったから、今後も絶対に意味が変わらないとは言えません。

ただ、少なくとも今回見つけた2種類の回帰、

- 勝手な因果関係の追加
- 判断段階と確信度の変更

はv2.1では再発しませんでした。

## 安全性にはトークンコストがかかる

もう1つ、かなり分かりやすいトレードオフがありました。

安全ルールを増やすほど、毎回Geminiに渡すシステム指示が長くなります。

19ケースの制約付き入力トークンは次のように増えました。

| Prompt | 入力tokens / 19件 | レビューで見つかった問題 |
| --- | ---: | --- |
| Baseline | 7,340 | 明示されていない因果関係を追加 |
| v2 | 12,755 | 判断段階と断定度が変化 |
| **v2.1** | **17,980** | **今回の手動レビューでは重大な問題なし** |

これはかなり大きな差です。

一方、v2.1の19ケースでは平均APIレイテンシが728msでした。通常のGemini書き直しは765msだったので、この1回では極端な遅延増加は見えませんでした。

ただし、レイテンシも単発測定です。ここも一般化はできません。

個人的には、最終出力だけに使う薄いRendererなら、多少の入力トークン増加は許容しやすいと考えています。

毎回の推論全部をGeminiにやり直させるわけではないからです。

## この設計で一番大事だったこと

作ってみて、一番重要だったのは「いいプロンプトを書くこと」ではありませんでした。

**どこまでをLLMに任せて、どこからをコードで固定するかを決めること**でした。

数字やURLを守るなら、お願いするよりロックする。

Markdown構造を見るなら、LLMに聞くよりコードで比較する。

文章の意味を見るなら、構造検証と混ぜずに別のレビュー工程にする。

そして、Geminiには調査も判断もさせない。

やらせるのは日本語の表面だけです。

この分業にしてから、かなり扱いやすくなりました。

## 現在の限界

まだ課題はあります。

今回は19件の固定コーパスを各プロンプトで1回ずつ評価しただけです。自然さについても、明示的な人手スコアをまだ付けていません。

次にやるなら、実際のCodex出力をもっと集めて、複数回実行したうえで、

- 自然さ
- 意味保持
- 変更量
- レイテンシ
- APIコスト

を継続的に測る形にしたいです。

また、今はGeminiだけをRendererにしています。別モデルを増やすこと自体は難しくありませんが、まずは1つの構成を十分に評価する方を優先しています。

## まとめ

最終的な構成はかなり単純です。

```text
Codexで考え切る
  ↓
壊されたくない値をコードで保護
  ↓
Geminiで日本語だけ整える
  ↓
保護値を完全復元
  ↓
Markdownなどを機械検証
  ↓
Codexで意味を最終確認
```

普通のLLM書き直しは便利です。ただ、自然さと意味保持は同じ問題ではありません。

そこを分けて考えると、LLMを「もう一度考える人」ではなく「最後に文章だけ整えるレンダラー」として使えるようになります。

今のところ、この分け方が一番しっくりきています。
